# Presence suppression is derived, not stored; presence-schedule edits trigger retroactive reconciliation

A task occurrence's "is this Trackee even home for this?" state is **computed on read** from the current presence schedule (intersecting the occurrence's effective time-of-day — `due_time` if set, else `23:59` — against the schedule's home/away cells and per-day hand-off times). It is not stored on the occurrence. By contrast, **Excused** and **Deferred** *are* per-occurrence Admin actions and *are* stored.

This means a parent can retroactively add a forgotten vacation that covered last Tuesday, and last Tuesday's occurrences immediately re-classify as presence-suppressed without anyone manually touching them. Any Miss effects that had already fired on those occurrences (point deductions, ladder advances, Restrictions, streak breaks) are reversed by a reconciliation pass triggered on the presence-schedule write. Conversely, removing a vacation window re-evaluates affected past occurrences and may fire Misses for ones that are now past-deadline-and-not-suppressed.

The trade-off accepted: schedule edits become ledger-mutating actions, and a parent who edits the past sees historical points/restrictions change. We're choosing this over per-occurrence-stored suppression because the alternative (writing a suppressed-status record per task × day × Trackee for every away day) bloats storage, complicates one-off vacation entry, and forces an explicit "apply to history" mode. Reconciliation is bounded — only occurrences in the changed date range are touched — so the implementation cost stays small.
